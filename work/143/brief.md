## Context

Once each check is replayed in its own clean working tree (#133), the setup runs once per check and the checks still run one after another. In the benchmark on a reference project, the wall-clock time of an Ariane ticket was two to three times that of Claude Code used alone, the replay taking a large part of it. Checks that run in separate trees can run at the same time, as CI jobs do, provided they do not collide on the machine's local resources, which the run slot (#142) gives them a way to avoid. Spec: C9 (all checks run, one section per check, a final summary), C11, non-functional "Cost".

## Decided spec

- New optional key `project.parallel_checks` (positive integer, default 1): the number of checks replayed at the same time. 1 is today's order, one by one.
- With a value above 1, the per-check trees (setup then check) run in a pool of that many workers (threads, each running its processes through `process.run`). The results are recorded in the declared order, whatever the order they finish in; the report and the statuses are unchanged.
- **Slots.** Each worker holds its own run slot (taken as in #142) and gives it as `ARIANE_SLOT` to its setup and check, so two checks of one run never share a slot. When fewer slots are free than `parallel_checks`, the run uses as many workers as it got slots (at least the one the run already holds) and journals it.
- A stop (a setup failure, Ctrl-C, a guard failure) stops the other workers, kills their process trees and removes every tree, as for one check today.
- `ariane verify` follows the same key.
- Ariane's own `ariane.toml` is not changed here (the owner chooses).
- A new ADR (next free number) records the key, why threads and not processes, and how slots are shared.
