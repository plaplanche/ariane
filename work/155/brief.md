## Context

In the benchmark on a reference project (`docs/benchmark.md`, #130), a blind quality review of lot 2 found the same race in all three complete attempts, Ariane's included: the result object is written to storage before the conditional statement that decides whether the lease is still valid, so a stale result can still write it, against a spec rule that orders exactly these steps. Two attempts out of three also left a race between refresh-token rotation and the revocation of the token family. The hidden black-box acceptance could not see these races, and neither could Ariane's reviewer: its prompt asks it to look for what is "wrong, missing or unsafe" in general, and nothing points it at the order of side effects, which is where concurrency bugs hide. Spec: C10 (adversarial review), C26.

## Decided spec

- Add one rule to the reviewer's prompt in `src/ariane/review.py`, right after the "Be adversarial" rule, with exactly this text:

  `- Check the order of side effects. Where the issue, the spec or the code relies on an order of operations, on atomicity, on idempotent retries or on concurrent requests (words such as "before", "after", "in one statement", "atomically", "only if", "never overwritten", "retry", "concurrent"), follow each request path step by step and list every write (database, storage, files, external calls, logs) in the order it happens. A write that happens before the check that should guard it, a decision split across separate statements that a concurrent request can interleave, or a retry that can write twice is a blocking finding; name the two steps and the interleaving that breaks them.`
